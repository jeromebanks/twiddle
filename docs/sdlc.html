How an issue ships

twiddle's issue workflow, for the people in it. Someone files an issue on GitHub, and it goes through a sequence of states until the change is on main and the issue is closed. This page covers every state, whose move each one is, and the skill that moves it on.

1. Who's involved

The poster

The person who filed the issue. They're treated as an end user: they answer questions, sign off a plain-language spec, and say /approve or /changes to each demo. They never review code or plans.

The agent

A Claude Code session running one of four skills. It writes specs, plans, code and demos. It only talks to people through comments on the issue, never in the chat, so an orchestrator can run it unattended.

Codex, the reviewer

A second, independent model that reviews read-only. It reviews every plan, every pull request, and every milestone before it ships. Nothing it hasn't approved gets built, merged or shipped.

tools/sdlc.py

The deterministic half. It derives an issue's state from its labels and comments, enforces every gate, and makes every label change, comment, merge and release. Skills ask it what to do next, and nobody works that out by hand.

A maintainer

Steps in only when the tooling says a human is needed (sdlc:escalated), or to run a demo step that makes a real speaker play.

2. The whole journey

Each issue carries exactly one sdlc:* label, which says where it is. Blue boxes are the agent's move, orange are the poster's, and red needs a human.

3. Every state, and what moves it on

Whose move it is comes from tools/sdlc.py, which reads it off the label and the comments. "Action" is the name state N prints. The skill named under "next" is what to run.

LabelWhose moveWhat happensAction → next
(none) / sdlc:triageagent The agent reads the issue and the code. If it's unclear, it asks questions. If it's a feature, it writes a PRD. If it's a bug, it reproduces it read-only and writes a diagnosis. triage → /triage-issue N
sdlc:needs-infoposter Questions are waiting for the poster. Their reply makes it the agent's move again. wait_for_poster, then respond_to_reply → /triage-issue N (or replan → /plan-issue N for a planning question)
sdlc:prd-review / sdlc:diagnosis-reviewposter A revision is posted. The poster replies /approve, /changes …, or just comments. Each revision spends a round, up to max_rounds. record_approval or respond_to_reply → /triage-issue N
sdlc:approvedagent The approved PRD is merged into docs/prd/. The agent plans the work as subtasks and one-session slices, grouped into milestones, each rated for complexity. Codex reviews the plan round by round until it approves. The poster isn't asked to review it. plan, continue_plan, create_plan_issues, ask_poster → /plan-issue N (reconcile_label when a maintainer ticked the label by hand)
sdlc:plannedagent plan-create has made the first milestone's issues and the branch epic/N. work_slices → /work-slice S
sdlc:in-progressagent Slices are built one per session. When a milestone is complete, it's demoed. Once accepted, it ships to main. Then the next milestone is planned and built. work_slices → /work-slice S, /milestone-demo N, sync N, or /plan-issue N (plan_next_milestone, --cleanup, or demo feedback)
sdlc:in-progress with a demo requesta person A demo step would make a real speaker play, so the agent asks on the issue for someone to run it and say what they heard. wait_for_poster, then demo_heard → /milestone-demo N
sdlc:demo-reviewposter A milestone demo is posted, with real screenshots. The poster tries it. record_demo_acceptance or demo_reply → /milestone-demo N
sdlc:donenobody Every milestone was accepted and shipped. epic/N is deleted and the issue closed. none
sdlc:escalateda human The agents couldn't agree, a merge of main conflicted, a suite failed on the epic branch, or a plan amendment ran out of rounds (escalate_plan). A human resolves it and moves it back to triage. human (and fix_conflict when two labels clash)

The slices themselves (plan:slice, plan:subtask) and filed tech-debt are never triaged on their own. They move with their epic.

4. The four skills

Each skill does one stage and ends by printing the next: line, so the next session (or an orchestrator) knows exactly what to run.

SkillRuns whenMoves the issueThrough these tool steps
triage-issuenew, triage, a reply in review untriaged → triage / needs-info → prd-review or diagnosis-review → approved state, transition, reconcile, merge-prd
plan-issueapproved, the next milestone, demo changes, a cleanup pass approved → planned, or adds issues while in-progress plan-validate, plan-post, plan-review, plan-create, plan-annotate, bootstrap-labels
work-slicea slice is ready planned → in-progress (first claim). The slice goes from ready to merged. slice-status, slice-check, claim, test-record, pr-review, merge, cleanup, release, escalate-slice, file-issue, ready
milestone-demoa milestone is complete, the poster replied, or an accepted one is due to ship in-progress ⇄ demo-review. The last ship makes it done. demo-status, demo-request, demo-post, demo-accept, demo-changes, sync, ship-review, ship, verify-main, revert-slice, file-issue

Also: epic-branch N gives an older epic its branch, next lists every issue where it's the agent's move, and state N explains one.

5. A slice, from ready to merged

A slice is one unit of work, sized for one session. Its issue is the whole brief: outcome, scope, acceptance criteria, how to validate it, the demo, the non-goals and the context.

  1. Claim. claim S --model … posts the claim, assigns it, and makes a worktree on slice/S from origin/epic/N. It refuses while a demo or release is due, a slice of a later milestone is waiting, or the cleanup pass comes first.
  2. Build. Only what the brief says, with offline tests. No test touches the network, a speaker or Spotify, and nothing fires on a real speaker.
  3. Test. test-record PR runs the full suite on the pushed head and records the result on the PR.
  4. Review. Codex reviews that exact head. Each round is recorded with pr-review before any fix is pushed. Fixing or rebutting continues until Codex approves the current head. After max_pr_rounds (5 by default) rounds asking for changes the slice escalates. If it was built on a cheaper model, it's retried once on the strongest.
    Two kinds of slice skip this and are reviewed with their milestone instead. A slice rated complexity:routine is one (slice_review in the config). A slice whose PR Codex couldn't review is the other: Codex wasn't installed or signed in, was out of quota, or timed out. review-defer PR --reason … records that, but never after Codex asked for changes nobody has answered.
  5. Merge. merge PR is the gate: the PR targets epic/N and isn't behind it, Codex approved this head (or its review is owed to the milestone, which merge records on the epic first), tests passed on it, and it belongs to the current milestone. Then the slice is squash-merged into epic/N and its issue closed. Non-blocking findings are filed as tech-debt first.

Several at once

Each slice is built in its own git worktree, a second checkout of the repo on its own branch, in .worktrees/slice-S. claim makes it and cleanup removes it. It isn't Claude Code's own worktree feature: that one branches from main, and a slice has to start from epic/N. The main checkout stays on main, untouched, so several sessions can work side by side:

  • Different issues run independently. Open one Claude Code session per issue or slice, all started in the main checkout. ready lists what can be claimed.
  • Slices of one epic run in parallel within the milestone being built. A slice that needs another's code waits for it.
  • Two sessions can't take the same slice: claim refuses one that's already claimed. Claim from one machine, because two machines claiming in the same few seconds could both get through.
  • Merges happen one at a time. The second slice to finish rebases onto epic/N and is tested and reviewed again.
  • Demos happen one at a time, because a demo uses the real speakers, with the poster there.

The full table of worktrees, and what holds each one, is in SDLC.md → "Worktrees, and several sessions at once".

6. A milestone, from plan to main

A milestone is a group of slices that ends in something the poster can see. The epic works on one milestone at a time, the earliest one not yet shipped. Only its slices are offered, claimed or merged.

What's due, in order

For the current milestone, next always picks the first of these that applies:

  1. Verify main, if a release reached it with commits no recorded run saw, because main moved during ship. verify-main N runs the suite on main. Until it passes, nothing else starts and the epic can't finish.
  2. Plan it (uncreated). By default only the first milestone's issues are created up front. Each later one is replanned with a Lessons from M1 section and a fresh Codex review, then created. /plan-issue N.
  3. Review it (review), when some of its slices were merged without a review of their own. /milestone-demo N syncs epic/N and has Codex review the milestone, reading each of those slices as closely as a pull request (ship-review). Nothing is shown to the poster until Codex approves. A blocking finding becomes fix slices.
  4. Demo it (complete or demoed). /milestone-demo N runs the demo steps from epic/N, with main as the "before". It draws real screenshots and posts the demo for the poster.
  5. Ship it (accepted). sync N merges main into epic/N and runs the suite. Codex reviews the milestone's whole diff (ship-review). Then ship N merges epic/N into main through a pull request, with a merge commit.
  6. Pay down debt (just after the previous milestone shipped, when tech debt is open). /plan-issue N --cleanup plans up to cleanup_slices_per_milestone debt slices, and they go before the rest of this milestone.
  7. Catch up with main. When nothing's ready or in flight and epic/N is behind, sync N.
  8. Build it. /work-slice S for the first slice on offer, named with the model its rating maps to, e.g. (sonnet: routine).

7. Branches: nothing unseen reaches main

  • Slices never touch main. A slice's PR targets epic/N. A bad slice is undone with one revert commit there (revert-slice S, tested before it's pushed), which reopens the slice and voids its milestone's demo.
  • sync N merges main in. It never rebases, because slice branches are built on epic/N. It runs the full suite and records it, and pushes only on a pass. A conflict or a failure goes to a human.
  • ship N releases one accepted milestone. It needs all of these:
    • epic/N contains main;
    • a passing run on its head;
    • Codex's approval of the milestone's diff on that same head;
    • every commit on the branch traces to a slice of an accepted milestone: its squash, a cherry-pick -x of one, or a revert of one. A merge has to be a clean merge of main. One that resolved a conflict ships only after a human has reviewed it (--accept-merge).
    It rechecks main right before merging, and checks the merge afterwards. If main moved in that moment, the release is marked untested and the epic is escalated. Nothing more happens until verify-main N passes on main.
  • A milestone built before epic branches existed, straight onto main, ships as a recorded no-op, with no sync and no Codex review: nothing of it is on the branch, so a review would judge a later milestone's code.

8. Problems found along the way

Nothing found is left in a chat or buried in a PR. It's sorted, and each kind has its own path:

FoundWhat happens
Broken. Something this milestone promised fails at its demo. No demo is posted. demo-changes N --found records it, plan-issue plans fix slices (each with a test that reproduces it), and the demo runs again.
Non-blocking. A cosmetic problem, an edge case, a review suggestion, or an adjacent issue. file-issue N --debt files it as tech-debt, linked to the epic. A budgeted cleanup pass picks it up after the milestone is accepted, and merge closes it with the slice that pays it down.
Out of scope. A bug that already existed, or one in another feature. file-issue N makes a new issue, which starts its own journey at triage.
The poster wants something different. Their /changes becomes new slices in the same milestone, then demo rev 2.

9. What you can type

/approve

On a line of its own. It signs off the latest PRD or diagnosis, or accepts the latest milestone demo. A newer revision voids an earlier approval.

/changes <what>

Asks for something different. On a demo, it becomes new slices.

Any reply

It's read as feedback or an answer. Replying with what you heard is how a demo step that plays on a real speaker gets confirmed.

Only the issue's author or someone with write access can /approve. Quoted and code-block lines don't count.

10. Where is my issue?

uv run python tools/sdlc.py state 12        # its state, whose move, and the next: line
uv run python tools/sdlc.py next            # every issue where it's the agent's move
uv run python tools/sdlc.py demo-status 12  # each milestone: its slices, before/after, demo and release
uv run python tools/sdlc.py ready --epic 12 # the slices that can start now

The next: line is always the answer to "what now?". Every skill ends by printing it.

11. A worked example

  1. Someone files "Sonos alarm manager" (#12). /triage-issue 12 asks two questions, and the issue becomes sdlc:needs-info.
  2. They answer. The agent writes PRD rev 1 (sdlc:prd-review), and they reply /approve. The PRD is merged into docs/prd/, and the issue becomes sdlc:approved.
  3. /plan-issue 12 writes a plan with three milestones. Codex asks for changes twice and approves rev 3. plan-create makes M1's slices and epic/12, and the issue becomes sdlc:planned.
  4. /work-slice 28, 29, 30: each slice is claimed, built, tested, reviewed by Codex, and squashed into epic/12. The issue is now sdlc:in-progress.
  5. M1 is complete, so /milestone-demo 12 posts screenshots of alarm list, and the issue becomes sdlc:demo-review. The poster says /approve.
  6. The agent runs sync 12, Codex reviews M1's diff, and ship 12 merges epic/12 into main. M1 is on main.
  7. /plan-issue 12 replans M2 with Lessons from M1, plus one tech-debt cleanup slice. Then the loop repeats. One of M2's steps rings a real alarm, so the agent asks on the issue, and the poster replies "it rang at 7:02".
  8. When the last milestone ships, epic/12 is deleted, the issue becomes sdlc:done, and it's closed.

12. The rules that hold it together

  • One label at a time. Every sdlc:* label is changed only by tools/sdlc.py. The labels are sdlc:triage sdlc:needs-info sdlc:prd-review sdlc:diagnosis-review sdlc:approved sdlc:planned sdlc:in-progress sdlc:demo-review sdlc:done sdlc:escalated.
  • Markers are the record. Every agent comment starts with a hidden <!-- sdlc:v1 kind=… --> marker. The state is read back from those markers, so any session can pick up an issue from GitHub alone.
  • Records are bound to commits. A test run or a Codex review counts only for the exact commit it saw. A new commit voids both.
  • People are reached through the issue. No skill asks a question in the chat. Publishing a demo is gated by automated checks (no device IDs, addresses or secrets, no blank pictures), and the poster's reply is the human check.
  • Speakers are safe. Tests are offline. Agents run only read-only and --dry-run commands. A real speaker plays only when a person runs the command, between snapshot and restore, and what they heard is recorded.
  • One view decides. next and every gate read the same epic view, so they can't disagree. A test checks that over thousands of generated histories.

Reference: SDLC.md, the skills under .agents/skills/, and tools/sdlc.py. This page is checked by tests/test_sdlc_guide.py: a new label, command, skill or milestone phase that isn't described here fails the suite.
